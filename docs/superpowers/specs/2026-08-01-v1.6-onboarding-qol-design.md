# RackStack v1.6 — Onboarding & Quality of Life Design

**Date:** 2026-08-01
**Status:** Approved by owner (NeverEndingCode) 2026-08-01.
**Scope:** A post-expansion release. The v1.2–v1.5 expansion
(`docs/superpowers/specs/2026-07-25-rackstack-expansion-design.md`) is complete and shipped; this
document does not extend it. It covers one new subsystem (a guided **tour framework**) and four
targeted fixes to existing behaviour.

---

## 1. Goal

Five items, requested by the owner:

1. **A tutorial for new players** that walks them through the game's features, which also fires
   once for existing players. Architected so future releases can ship a *small* tour covering only
   the new feature, without anyone re-watching the full tutorial.
2. **The Overheat popup auto-dismisses** after 15 seconds, configurable from the Balancing tab.
3. **The vent button cools by a percentage** of heat capacity rather than a flat amount, also
   configurable from the Balancing tab.
4. **The Racks "Collect" button stays visible** until the tier is automated, instead of vanishing
   for a split second after each collect.
5. **A literal `&middot;` is rendered in the Racks tab** and must show `·`.

## 2. Inherited constraints

Carried forward from v1.2–v1.5 and not up for renegotiation:

- **All math lives in `shared/`** — pure ESM, zero runtime dependencies, consumed identically by
  the server (authoritative) and the client (rendering). The client never computes a payout.
- **Server-authoritative via lazy evaluation.** Game-state changes go through reducer actions
  validated in `POST /api/actions`. Every handler keeps the `(s, action, config, now)` contract,
  mutates the already-`structuredClone`d `s`, and returns `{ok:true, …}` or `err('code')`.
- **No new reducer error strings.** Reuse `invalid_target`, `not_met`, `max_level`,
  `insufficient_credits`, `cooldown_active`.
- **Every index or key taken from a request payload is validated before any property access.**
- **Numbers are config-driven.** New tunables go in `shared/configSchema.js` so the Balancing tab
  edits them and live events can overlay them.
- The stored config document is never written with event modifiers merged in.

## 3. The design decisions

Resolved by the owner before this document was written:

| Fork | Decision |
| - | - |
| Tutorial presentation | **Spotlight coach-marks** — a dimming overlay cuts a hole around the real UI element, with a tooltip bubble and Back/Next/Skip. Not a slide carousel, not a quest chain. |
| Tutorial scope | **Full tour, unlock-aware** — every tab including Cold Storage, Games, Social, Singularity and Events, with steps auto-skipped when that content is still locked for the player. |
| Rollout to existing players | **Auto-start, easily skipped** — it launches on next login for anyone whose flag is unset, with a visible Skip on every step. |
| Architecture | **A tour framework, not a single tutorial.** The unit of completion is a *named tour*, tracked per-user as a set, so future releases ship a small feature tour that only shows the new feature. |

## 4. The tour framework

### 4.1 Data model

The unit of completion is a **tour**, identified by a stable string id. A user has a *set* of
completed tour ids, not a boolean.

**Column.** `users.tours_completed TEXT DEFAULT '[]'` — a JSON array of tour ids, added with the
existing `guardedAddColumn()` helper in `server/db.js`. This mirrors `users.roles` exactly,
including the defensive read: a corrupt or unparseable value reads back as `[]` rather than
throwing.

Existing players have no column value until the ALTER runs, then default to `'[]'` — an empty
completed-set, which is precisely what makes the onboarding tour fire once for them.

**Accessors** in `server/db.js`, modelled on `getRoles`/`setRoles`:

- `getToursCompleted(userId) -> string[]`
- `setToursCompleted(userId, ids)` — writes `JSON.stringify(ids)`.

### 4.2 Registry split: `shared/tours.js` vs `client/src/game/data/tours/`

The registry is deliberately split so the server can validate ids without importing JSX.

**`shared/tours.js`** — metadata only, no step content, no JSX:

```js
export const TOURS = [
  { id: 'onboarding', label: 'Full tutorial', description: '…', autoStart: true },
];
export const TOUR_IDS = TOURS.map((t) => t.id);
export function isValidTourId(id) { return TOUR_IDS.includes(id); }
```

**`client/src/game/data/tours/`** — one module per tour, holding the step content:

- `steps/*.js` — reusable step arrays grouped by feature area (`welcomeSteps`, `racksSteps`,
  `gridSteps`, `overclockSteps`, `upgradesSteps`, `goalsSteps`, `gamesSteps`, `coldStorageSteps`,
  `socialSteps`, `singularitySteps`, `migrateSteps`, `eventSteps`, `wrapUpSteps`).
- `onboarding.js` — the composition that imports those step arrays in order.
- `index.js` — exports `CLIENT_TOURS`, keyed by the ids in `shared/tours.js`.

**Steps are the reusable unit.** A future feature tour writes its steps once, registers them as a
standalone tour for existing players, and appends the same array into `onboarding.js` for new
players. No tutorial copy is ever written twice, and the two paths cannot drift.

A dev-time invariant test asserts `Object.keys(CLIENT_TOURS)` and `TOUR_IDS` are the same set, so
a tour registered in one place but not the other fails the suite rather than silently never firing.

### 4.3 Step shape

```js
{
  id: 'racks-collect',        // unique across all steps
  tab: 'racks',               // tab to switch to before showing; null = no switch
  anchor: 'racks-collect',    // matches data-tour="racks-collect"; null = centered, no hole
  title: 'Collect your FLOPS',
  body: 'Racks bank output until you collect it. …',
  visibleWhen: (ctx) => true, // optional; omitted means always visible
}
```

`visibleWhen` receives the unlock context described in §4.5. Steps whose predicate returns false
are removed from the run *before* it starts, so the `n / total` counter reflects only the steps
that player will actually see.

A tour may also carry an optional `availableWhen(ctx)` predicate, used by §4.6 to decide whether
the tour fires at all. It lives on the client-side tour module next to `steps`, not in
`shared/tours.js` — that file stays serialisable metadata the server can import.

### 4.4 Anchoring: `data-tour` attributes

Anchors are matched by `document.querySelector('[data-tour="<anchor>"]')` rather than React refs
threaded through every panel. This keeps the change to each existing panel to a single attribute
and avoids restructuring components that are otherwise untouched by this release.

Attributes to add:

| `data-tour` | Location |
| - | - |
| `header-stats` | `HeaderBar.jsx` — the FLOPS / rate readout |
| `racks-buy` | `RacksPanel.jsx` — the +1 / +10 / Max row |
| `racks-collect` | `RacksPanel.jsx` — the Collect button |
| `racks-automate` | `RacksPanel.jsx` — the Automate button |
| `grid-buy` | `GridPanel.jsx` — the buy row |
| `overclock-heat` | `OverclockPanel.jsx` — the heat gauge card |
| `overclock-vent` | `OverclockPanel.jsx` — the Vent button |
| `upgrades-list` | `UpgradesPanel.jsx` |
| `goals-list` | `GoalsPanel.jsx` |
| `games-list` | `GamesPanel.jsx` |
| `coldstorage-track` | `ColdStoragePanel.jsx` |
| `social-sections` | `SocialPanel.jsx` |
| `singularity-list` | `SingularityPanel.jsx` |
| `migrate-bar` | `MigrateBar.jsx` |
| `event-ladder` | `EventPanel.jsx` |

An anchor that resolves to nothing is **not** an error: the overlay degrades to a centered tooltip
with no spotlight hole for that step. A tour must never trap or blank the UI because a panel
changed shape.

### 4.5 Unlock context

`RackStack.jsx` already computes the predicates the tour needs (currently at lines 978–981). They
are passed to the tour system as a single `ctx` object rather than recomputed:

```js
const tourCtx = {
  gridUnlocked, overclockUnlocked, singularityUnlocked, coldStorageUnlocked, eventLive,
};
```

This gives the framework a genuinely useful property beyond skipping: a feature tour for content
the player has not unlocked does not fire and get wasted — it stays pending and triggers the
moment that player unlocks the feature.

### 4.6 Selection rule

1. Build the candidate list: registered tours, in registry order, that are **not** in the user's
   `toursCompleted`, have `autoStart: true`, and whose `availableWhen(ctx)` passes (a tour with no
   `availableWhen` is always available).
2. Start the first candidate. **At most one tour runs at a time.**
3. After a tour completes or is skipped, do **not** auto-start another until the next app load, so
   a player is never carpet-bombed with several tours back to back.

### 4.7 Onboarding completion marks all registered tours complete

When the tour with id `onboarding` is completed *or skipped*, every id in `TOUR_IDS` is written to
`tours_completed`, not just `onboarding`.

**Rationale.** A brand-new player who takes the full tour would otherwise be handed each feature
tour immediately afterwards, covering ground they just saw. This is correct precisely because of
the composition rule in §4.2: the onboarding tour always contains the feature tours' steps.

**The maintenance obligation this creates is explicit:** when a future release adds a feature tour,
its steps *must* also be appended to `onboarding.js`. The §4.2 invariant test does not catch this;
a comment at the top of `onboarding.js` states the obligation.

Skipping counts as completing, for all tours. A player who skips has made their choice, and
re-showing a tour they dismissed is the more annoying failure mode.

### 4.8 API

**`GET /api/me`** gains one field:

```js
toursCompleted: string[]   // from users.tours_completed, [] on corrupt/missing
```

**`PUT /api/me/tours`** — one endpoint serving both "finished it" and "replay this one":

```
body: { tourId: string, completed: boolean }
200:  { ok: true, toursCompleted: string[] }
400:  { error: 'invalid_request' }   // non-string tourId, non-boolean completed,
                                     // or tourId not in shared/tours.js TOUR_IDS
401:  (requireAuth)
```

`completed: true` adds the id (and, for `onboarding`, all of `TOUR_IDS` per §4.7);
`completed: false` removes it. The set is deduplicated on write, and unknown ids already present in
the stored array are preserved rather than dropped — a rolled-back deployment must not erase a
newer tour's completion.

This is a **pure UI preference**. Unlike v1.4's leaderboard opt-out, it is *not* mirrored into the
save document and gets no reducer action: it has no game-state implications, and keeping it out of
the reducer keeps the save schema untouched by this release.

### 4.9 The overlay component

`client/src/game/components/TutorialOverlay.jsx`.

- Resolves the current step's anchor, calls `scrollIntoView({ block: 'center' })`, then measures
  with `getBoundingClientRect()`.
- Renders a fixed, full-viewport dim layer with an SVG mask cutting a rounded-rect hole over the
  anchor, plus a tooltip card containing the title, body, an `n / total` counter, and
  **Back** / **Next** / **Skip**. The final step's Next reads **Done**.
- The tooltip is placed below the hole, flipping above when it would overflow, and is clamped to
  the viewport on both axes so it is never partly offscreen.
- Recomputes geometry on `resize`, on `scroll` (capture phase), and after a tab switch — the tab
  switch is applied first, then measurement happens on the next animation frame so the new panel
  has laid out.
- Clicking the dim layer does **not** advance or dismiss. Only the buttons do. `Escape` skips.
- The overlay is rendered above the app but **below** nothing else it needs to compete with; it
  takes a `z-index` above `ModalRoot`'s `z-40`.

### 4.10 Control flow in `RackStack.jsx`

- On the `/api/me` response, evaluate §4.6 against `toursCompleted` and `tourCtx`; if a tour is
  selected, set it active.
- The overlay drives `setActiveTab` as it advances.
- Finishing or skipping hides the overlay **immediately** and fires `PUT /api/me/tours`
  optimistically. A failed write is logged and otherwise ignored: the worst case is the tour
  re-offering on next load, which is strictly better than blocking the player on a network call.
- The tour does not start while a modal is open; it waits until `modal` is null. This prevents the
  spotlight from fighting the offline-earnings "Welcome back" modal on first load.

### 4.11 Replay from Profile

`ProfileSettings.jsx` gains a **Tutorials** block listing every registered tour with its completion
state and a **Replay** button. Replay writes `{ tourId, completed: false }` and starts that tour
immediately, bypassing the §4.6 "wait for next app load" rule (the player explicitly asked).

## 5. Overheat popup auto-dismiss

**Tunable.** `heat.overheatPopupMs`, default `15000`.

```js
{ path: 'heat.overheatPopupMs', label: 'Overheat popup duration (ms)',
  min: 0, max: 600000, integer: true }
```

`0` means the popup stays until dismissed manually — the pre-v1.6 behaviour, preserved as an
explicit setting rather than lost.

**Implementation.** `ModalRoot.jsx` takes a `meltdownAutoDismissMs` prop (passed from
`RackStack.jsx`, which holds config) and runs a `useEffect` timer. The effect keys on the modal
identity and the timeout callback re-checks that the meltdown modal is still the one showing before
clearing it, so a modal that changed underneath the timer is never dismissed by it. The timer is
cleared on unmount and on any modal change.

## 6. Percentage-based vent

**`heat.ventAmount: 500` is replaced by `heat.ventPercent: 25`.**

```js
{ path: 'heat.ventPercent', label: 'Vent amount (% of capacity)',
  min: 1, max: 100, integer: false }
```

25% of the default 2000 capacity is 500 — identical strength at defaults, so this is not a balance
change at stock settings. What changes is that venting now *scales*: with Summer Surge's
`heat.capacity: 4000` overlay or a maxed Heat-Sink Tapes bonus, a flat 500 was progressively
diluted, and a percentage is not.

**Reducer.** `vent()` in `shared/reducer.js` keeps both existing cooldown guards, then:

```js
const csEff = computeColdStorageEffects(s.meta);
const capacity = config.heat.capacity + csEff.heatCapacityBonus;
s.run.heat = Math.max(0, s.run.heat - capacity * config.heat.ventPercent / 100);
```

The capacity expression is *exactly* the one `shared/state.js:248` uses for the overheat threshold.
Both must include the Cold Storage bonus or venting would be measured against a different ceiling
than the one that triggers a meltdown. `computeColdStorageEffects` is already imported in
`shared/reducer.js`.

**Migration is free.** `upgradeConfig()` (`shared/configSchema.js:205`) rebuilds from
`DEFAULT_CONFIG` and copies only paths present in `TUNABLES`. Removing `heat.ventAmount` from
`TUNABLES` means a stored value is dropped on next load and `heat.ventPercent` picks up its default.
No migration code, and a config-history rollback to a pre-v1.6 version is equally safe.

**Accepted cost:** an admin who had tuned `ventAmount` away from 500 loses that tuning and lands on
25%. This is unavoidable when the unit changes, and is called out in the changelog.

**UI.** In `OverclockPanel.jsx`:

- The Vent button label becomes `Vent Heat (-25%)`, reading live config rather than a constant.
- The explainer paragraph currently hardcodes *"freezes for 10s"*; it reads
  `heat.overheatCooldownMs` instead. Same paragraph, same feature area, and it is already wrong for
  any admin who retuned the lockout.

## 7. Collect button always visible

`RacksPanel.jsx` currently renders the Collect button only when `!ts.manager && ts.ready > 0.01`,
so it unmounts for the frame after a collect and pops back when output accrues — the flicker the
owner reported.

The `ts.ready > 0.01` test moves off *visibility* and onto *disabled*, leaving the render condition
`!ts.manager && ts.owned >= 1` — the same gate the adjacent Automate button uses, so the two
buttons appear and disappear together. The button greys out via the existing `buyBtnStyle`
disabled treatment instead of vanishing, and the label still shows the live `Collect {fmt(ts.ready)}`.

The `collect-pop` entry animation only plays on mount; with the button permanently mounted it plays
once per tier rather than on every collect. This is the intended outcome — the animation was
incidentally firing as a side effect of the remount bug.

## 8. The `&middot;` bug

`RacksPanel.jsx:32` reads:

```jsx
{fmt(rate)} F/s{ts.manager ? ' &middot; automated' : ''}
```

The entity sits inside a **JavaScript string literal**, where JSX does not decode entities — it
decodes them only in literal JSX text. The ~40 other `&middot;` occurrences in the codebase are all
in JSX text and render correctly, which is exactly why the owner sees this only in the Racks tab.
Fixed by using the literal `·` character.

**Regression guard.** A test scans `client/src/**/*.jsx` for HTML entities inside quoted strings
(`/'[^']*&[a-z]+;[^']*'/` and the double-quote and backtick equivalents) and fails with the
offending file and line. Cheap, and it catches the whole class rather than this one instance.

## 10. Out of scope

- No changes to the save document schema, and no new reducer actions.
- No changes to the economy beyond §6's unit change (which is balance-neutral at defaults).
- The known deferred issue where `UpgradesPanel.jsx` and `SingularityPanel.jsx` read upgrade max
  levels from static defs instead of live config is **not** addressed here.
- No analytics on tour completion or drop-off. If that is wanted later, the JSON column should
  become a `user_tours(user_id, tour_id, completed_at)` table; nothing in §4.8's API shape prevents
  that swap.
